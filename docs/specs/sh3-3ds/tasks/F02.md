**Requisitos:** RF01.02, RF02.01, RNF07.06-RNF07.09 y RNF11.05-RNF11.09. Verificación V01/V02/V20/V21/V22/V25 y T01/T02 según alcance de esta instancia.

**Dependencias/entradas:** G00 aprobada, perfil PS2 canónico y SHA-256 completo de imagen previamente identificado; adaptador pycdlib 1.22.0 ya fijado y probado. Se abre la copia privada en lectura; no se necesita otra copia ni raíz de extracción para producir exclusivamente metadatos. Cualquier exportación posterior de originales requiere raíz privada externa explícita.

**Artefactos:** `tools/inspectors/{catalog,inventory,signatures}.py`, extensión de `tools/pipeline/iso9660.py`, `tests/python/test_inventory.py`, contrato y resumen revisado. Catálogos completos bajo `reports/local`, ignorados; reportes sintéticos bajo `build/f02-01`.

**Pasos detallados:**

1. `F02.01/contrato`: fijar esquema v1, unidad ISO, separación de origen/contenedor/offset y niveles de reconocimiento. Ningún ID ni contador permite afirmar que existe extractor, decoder o runtime soportado.
2. `F02.01/identidad`: exigir hash completo de imagen, plataforma PS2, conjunto exacto de rutas y cada tamaño/hash antes de leer prefijos para clasificación. Rechazar perfil parcial, entradas adicionales/duplicadas o contenido alterado.
3. `F02.01/ubicación`: exponer offset ISO verificado del adaptador existente; limitar a extents contiguos y rechazar multi-extent, atributos extendidos e interleave. Comprobar `offset + size <= image_size`. No interpretar estos offsets como estructura MFA.
4. `F02.01/IDs`: derivar ID SHA-256 de namespace, imagen completa, perfil y ruta; ordenar entradas. Bytes idénticos bajo rutas distintas mantienen identidad distinta. No incluir fecha ni rutas locales en el JSON determinista.
5. `F02.01/tipos`: clasificar prefijo de hasta 4096 bytes con reglas propias versionadas: configuración PS2 parseada, cabecera ELF32 LE MIPS, candidato AFS por firma o desconocido con motivo. Registrar extensión separada; no asignar formato MFA por nombre ni analizar tablas internas.
6. `F02.01/dependencias`: registrar únicamente la relación BOOT2 al ejecutable presente y compatible con serial/cabecera. Marcarla parcial; restantes entradas con `not_inspected` y lista de conocidos vacía. Ninguna lista vacía certifica independencia.
7. `F02.01/errores`: usar datos propios para firma engañosa/truncada, variante ELF, vacío, rango inválido, fallo de lectura, cambio durante inspección y destino existente. Comparar contrato del lector en memoria con ISO sintético y verificar offsets contra bytes conocidos.
8. `F02.01/catálogo-real`: ejecutar dos veces sobre la ISO europea solo en lectura, con destinos JSON nuevos. Comparar bytes completos de ambos informes; conservar hashes de evidencia, identidad de imagen/perfil, versiones y resumen por tipos. No guardar prefijos ni contenido de recursos en reportes.
9. `F02.01/calidad`: ejecutar batería Python, gates independientes de líneas/ramas ≥80 %, Ruff y contratos de arquitectura/custodia/specs. CI quality recoge las pruebas con fixtures sintéticos sin rutas privadas. No recompilar runtime C++ si no cambió.
10. `F02.01/cierre`: marcar esta instancia como inventario ISO completo; trasladar interpretación de MFA y otros contenedores a F02.02/F02.03 y sus entradas/dependencias a F02.04. Extracción repetible/corpus siguen F02.05-F02.07; Q05/G02 permanecen abiertos.

**Diseño SOLID:** `signatures` decide sobre bytes acotados; `inventory` coordina un puerto lector y el perfil; `IsoImage` posee archivo/recorrido/hash/offset/estabilidad; CLI compone y persiste JSON exclusivo después del cierre estable. Se reutilizan hashing, parseo de perfil y BOOT2. No se duplica el lector ISO ni se agrega SDK al núcleo.

**Aceptación y límites:** los dos catálogos son idénticos, todos los archivos del perfil verificados y desconocidos explícitos. La firma AFS no valida su tabla ni payloads; la cabecera ELF no valida ABI, relocaciones ni ejecución. La única relación conocida no es un grafo completo de dependencias. Datos originales y catálogo completo no forman parte de CI ni se publican. Siguiente tarea: **F02.02 — evaluar extractor MFA candidato**, con revisión de procedencia y ubicación externa antes de exportar datos.

**Criterios a concretar en el contrato antes de implementar:**

- WHEN se solicita exportación THEN el sistema SHALL verificar identidad completa, selección y concordancia del catálogo con los descriptores actuales antes de escribir recursos.
- IF el destino coincide con, contiene o está dentro del checkout, tiene enlaces, ya contiene datos o no satisface el presupuesto THEN el sistema SHALL rechazar la operación sin sobrescribir archivos.
- WHEN exporta una entrada THEN el sistema SHALL usar un nombre derivado de su ID estable, copiar exactamente el rango validado con memoria acotada y comprobar tamaño/hash de salida.
- IF ocurre truncamiento, cambio de origen, falta de espacio o error de lectura/escritura/verificación THEN la ejecución SHALL quedar fallida y no emitir un manifiesto de extracción aceptada.
- WHEN ambas ejecuciones finalizan THEN la comparación SHALL exigir el conjunto exacto de IDs, tamaños y hashes contra el catálogo y entre las dos copias, manteniendo desconocidos y exclusiones explícitos.

Separar campos deterministas de ubicación/fecha de ejecución. Definir si se retienen parciales para diagnóstico y cómo distinguirlos de una copia válida; nunca limpiar datos previos del usuario.
2. `F02.05/destino`: recibir la raíz privada externa como argumento explícito; comprobar relación con el checkout, componentes y enlaces mediante las políticas existentes, y reservar dos subdirectorios nuevos/exclusivos. 3. `F02.05/presupuesto`: sumar tamaños verificados y consultar espacio libre antes de comenzar. El mínimo observado para ambas copias es 3.124.735.680 bytes de payload, más manifiestos, asignación por bloques y margen documentado. Fallar si no cabe; gestionar ENOSPC también durante escritura, porque una comprobación previa no reserva espacio.
4. `F02.05/preflight`: verificar ISO/perfil/selección, versión/hash del catálogo y descriptores completos. Recalcular o contrastar cada ID/rango/tamaño y exigir el mismo conjunto aceptado. Rechazar catálogo alterado, entrada extra/faltante, rango fuera de contenedor y cambio de bytes. Ningún informe histórico sustituye la validación de la fuente actual.
5. `F02.05/copia`: implementar streaming acotado, creación exclusiva, ausencia de seguimiento de enlaces y comprobación de lecturas/escrituras cortas. Un recurso vacío produce un archivo vacío con hash correcto. Copiar bytes sin descompresión ni conversión y conservar trazabilidad ID → contenedor/rango/hash; no inventar extensiones semánticas.
6. `F02.05/verificación`: cerrar/releer cada salida y comprobar tamaño/SHA-256; verificar conjunto exacto de archivos y estabilidad final de la fuente.
